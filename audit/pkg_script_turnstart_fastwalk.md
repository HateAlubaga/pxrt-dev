# pkg_script_turnstart_fastwalk

Based on my analysis of the transpiled Autofastwalk.lua file and the runtime implementation, here's my audit report:

## Findings

- `Autofastwalk.lua:13` - high - **K.GS.Info.Teams access not implemented** - The script accesses `K.GS.Info.Teams[(w.WormTeam - 1)].Worms[(w.WormNumber - 1)].State` to check worm state (line 13). The runtime implements K.GS.Info.Teams as a proxy (pxrt_e_game.lua:126-158) that supports .Health and .State fields via __index metamethod, but this is a 0-based indexed table access pattern that should work. However, the State lookup reads from wormAddr + 0x44 which returns 135 for free slots (line 137-139). The script checks `State == 100` which appears to be checking for a specific worm state, but there's no validation that this state constant is correct for the pxrt implementation.

- `Autofastwalk.lua:6` - high - **CTurnGame::SetCurrentTeam override semantics differ from PX** - The script overrides `CTurnGame::SetCurrentTeam` which in pxrt is a no-op stub (pxrt_e_classes.lua:253: `CT.SetCurrentTeam = function() return 0 end`). The runtime implements team switching detection via polling in pxrt_e_hooks.lua:414-427: it watches the turn game's CurTeam field each M_FRAME and calls the override chain *after* WA already switched teams. This is documented as "WA switches teams internally, so script overrides...never ran" in PX. The fastwalk script calls `super(Team)` expecting to actually switch teams, but in pxrt this super() does nothing—the switch already happened before the override runs. The semantic is inverted: PX overrides run *instead of* the native switch; pxrt overrides run *after* the native switch with a no-op super.

- `Autofastwalk.lua:18-20` - medium - **F.GetWeaponByName may return stub weapon** - The script looks up "Fast Walk" weapon by name (line 18) and checks if null (line 19), but if the weapon doesn't exist in the game's weapon table, `F.GetWeaponByName` returns `E.weaponById(-1, "Fast Walk")` (pxrt_e_funcs.lua:150), which creates a weapon proxy with id=-1. This proxy won't be null, so the null check passes, but subsequent operations may fail silently or behave incorrectly.

- `Autofastwalk.lua:25` - medium - **w.WeaponN assignment may not reflect GetWeaponIndex result** - The script calls `mc(weap, "GetWeaponIndex")` and assigns the result to `w.WeaponN` (lines 25-26). The CWeapon proxy's GetWeaponIndex returns `id >= 2 and id - 2 or id` (pxrt_e_classes.lua:553-556), but for a weapon with id=-1 (invalid weapon), this returns -1, which is then written to the worm's WeaponN field (offset 0x170). This may cause issues if WA expects WeaponN to be a valid weapon index.

- `Autofastwalk.lua:22-23` - low - **CShootDesc struct creation uses memory buffer** - The script creates a CShootDesc struct with `__R__.struct("CShootDesc")` and calls `F.zero(sdesc)` (lines 22-23). The runtime allocates a 0x64-byte buffer from a pool (pxrt_e_structs.lua:45-78), and F.zero clears table fields but doesn't zero the memory buffer itself for structs with __a field (pxrt_e_funcs.lua:72-87, returns 0 at line 80 if __a exists). However, pxrt_e_structs.lua has a custom zero override (lines 279-298) that does call memFill for structs, so this should work correctly. This is not a bug, but the zero implementation is non-obvious.

- `Autofastwalk.lua:24-26` - medium - **CWorm.FireFinal call may not fire weapon** - The script calls `mc(w, "FireFinal", weap, sdesc)` expecting to fire the Fast Walk weapon (line 26). The CWorm.FireFinal method in pxrt sets a flag `E.fireFinalNative = true` and returns 0 (pxrt_e_classes.lua:231-234). The hook layer (pxrt_e_hooks.lua:530-588) implements the actual firing logic, but this is only called during the WA FireWeapon hook. Calling FireFinal directly from a SetCurrentTeam override (outside the fire weapon flow) may not trigger WA's weapon firing at all—the native fire path expects to be called from within WA's weapon firing sequence, not from a team switch event.

- `Autofastwalk.lua:27-31` - low - **Weapon restoration assumes lastWeap was non-null** - After firing, the script restores `w.CurWeapon` and `w.WeaponN` from saved values (lines 30-31), but only if `lastWeap` is non-null (line 27-28). If the worm had no weapon selected initially (CurWeapon was null), the script exits early without restoring, leaving the worm with the Fast Walk weapon selected. This might be intentional, but it's asymmetric—the weapon is changed even if there was no previous weapon, but not restored.
